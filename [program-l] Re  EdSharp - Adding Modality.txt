In EdSharp, the Frame class has a Dictionary field called hashKey that is defined on the following line:

public static Dictionary<Keys, ToolStripMenuItem> hashKey = new Dictionary<Keys, ToolStripMenuItem>();

It associates key combinations with menu items.  Almost every EdSharp command has an associated menu item.  A single event handler is used for all menu items.

Keystrokes are first processed in the following event handler:

public bool ProcessCmdKey_Helper(ref Message msg, Keys keyData) {

After custom processing for certain keys or repeated keys (to spell the message spoken by the prior key combination), the menu item object associated with the keys is obtained from the dictionary on the following line:

else if (hashKey.TryGetValue(keyData, out menuItem)) {

The PerformClick method of that menu item is then done, which sends processing to the following method:

public void menuItem_Click(object sender, EventArgs e) {

Most EdSharp commands are defined in that method, based on the menu item that was matched.

Different key modes might be possible by dynamically changing the hashKey dictionary or the processing in one of the methods mentioned above.

In case you use JAWS, you might first experiment by defining "layered" keys in JAWS (e.g., Insert+Key, AnotherKey).  The JAWS script could then send native EdSharp keys.  Just a thought.

> Hi,
>
> To everyone who has delved into the EdSharp code before, and especially to Jamel, I'm looking for some pointers and advice on the best way to do the following:
>
> I'm trying to add modal editing functionality to EdSharp so that more and simpler keyboard shortcuts can be implemented (among other things).
> What I want to achieve is to have EdSharp go into N number of different modes where keys pressed will get interpreted depending on the current active mode.
>
> For example, one mode could be Navigation mode (similar to VI vi normal mode) where the keys j and k would advance the cursor down and up one line respectively, where [ and ] would do the same as for the current Ctrl+Shift+B and Ctrl+B respectively (move to previous and next code block) and so on.
>
> So on one level it will open up the whole keyboard for additional commands tied to shortcuts, and on another level it will simplify existing behaviour by now doing the same thing but with a single keystroke, or a number of times via a numberic count preseeding the keystroke, as in 20 j which will go down 20 lines etc.
>
> In these alternate modes, EdSharp should not just print the characters as the keys are pressed, even if it's a key without a modifier, but rather lookup the appropriate function to execute.
>
> This will also reduce keyboard shortcut conflicts with other apps since now, a key that was usually just assigned to printing out an 'a' character on the screen could be performing anything at all, and perhaps a function that, in the standard behaviour of the editor would have required Ctrl+Shift+a (for example).
>
> Going into this Navigation mode could be as simple as enabling Modal behaviour from the Misc menu, then pressing the Escape key once, and to return to the standard behaviour could be as simple as pressing the Escape key again while in the special new Navigation mode.
>
> Currently I've added a menu option to the "Misc" menu, which when clicked announces that Modal behaviour is switched on. Before I can continue I need to understand the structure of the program better, else I'll implement things in the wrong places and just waste my time.
>
> Ideally I would like to keep things as generic and general as possible, allowing for config file setups to assign shortcut keys to modes and behaviours.
>
> This is my attempt at bringing the efficiency of VI-style text editing to EdSharp, and opening up the way for new and fresh ways of streamlining editing of large and coplex structured text like programs and XML documents.
> At the same time this will capitalize on all the work done on EdSharp already, with all the many, many great features.
>
> If vim and emacs could work nicely and easily on Windows this all would not be necessary, but the effort to get vim and emacs working properly in the GUI on Windows, talking through NVDA and spitting out Braille through NVDA just keeps on being this really immense problem for which I can't find a simple solution.
>
> There is sub optimal solutions for getting JAWS speaking in gvim (the gui of vim), but it's not ideal at all.
>
>
> The quest for the perfect text editor continues....
