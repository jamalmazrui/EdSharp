EdSharp Documentation and Code Audit -- 22 August 2026

What this is: a comparison of what the EdSharp documentation promises with what the code actually does, traced by reading the code and walking through what happens step by step. The sources audited are the current master branch: EdSharp.md (the user guide, including its catalog of 216 commands), EdSharp.cs and the support sources, EdSharp.ini (the converter tables), EdSharp.js, EdSharp_Setup.iss, and the Convert folder.

The short version: your memory of Open Other Format misbehaving is correct on BOTH counts you half-remembered -- it can show duplicate entries, and it fails -- and the code tracing found the exact reasons for each. Six code or configuration defects and three documentation defects are described below, each with the trace that convicts it, followed by the queued revisions.

How the audit was done

  • The command catalog in EdSharp.md (216 entries of the form "Name=Key, description") was parsed and cross-checked against every CreateMenuItem call in EdSharp.cs (216 menu items): names, keys, and the existence of a click handler for each.
  • The commands most likely to have drifted -- the conversion pipeline, the new Markdown commands, the evaluator, and the outside-the-editor open path -- were traced by hand from keystroke to result, using the real converter tables in EdSharp.ini and the real contents of Convert.

The Open Other Format investigation

The documentation says: "Press Control+Shift+O to open a file in a format other than plain text. A converter is invoked based on the file extension." The code path is: the handler shows a file dialog, then calls OpenOrActivateWindow with convert mode on, which calls COM.ConvertFile2String. That method reads the [Import] section of EdSharp.ini, keeps the entries whose names start with the file's extension, shows a pick list when there is more than one, and runs the chosen converter as a hidden command line, reading the output file it leaves behind.

Trace one -- a Word file, and why conversion FAILS today.

  • You pick Report.docx. The Import table offers docx2htm, docx2md, docx2txt, and so on. Suppose you pick txt.
  • The command line built is: Convert\Pandoc\pandoc.exe "Report.docx" -f docx -t plain -s -S -o (temporary file).
  • Every pandoc line in the Import and Export tables carries the -S switch. That switch existed in pandoc version 1 and was REMOVED in pandoc version 2 (year 2017); today's pandoc, which installPandoc fetches as the latest release, exits with an error when it sees -S and writes no output file.
  • The code sees no output file, retries the same command through cmd.exe, fails again, and shows the error box "Command line:" with the command text. No conversion happens.
  • Verdict: every pandoc-based import and export -- Word, EPUB, HTML, Markdown, LaTeX, MediaWiki, reStructuredText targets -- fails with the currently installed pandoc. This alone explains "not working right."
  • Two smaller problems ride along: the epub3 entries pass "-f epub3", which is not a pandoc input format name (the reader is "epub"), and the markdown entries use "markdown_github", a name pandoc has deprecated in favor of "gfm" and may drop entirely.

Trace two -- an HTML file, and where the DUPLICATE entries come from.

  • You pick Page.htm. The Import table has htm2md, htm2mw, htm2rst, htm2tidy, htm2txt, and htm2tex. The code also adds the bare names rtf, htm, html, and xhtml to the working list before filtering, so that those types are always offerable.
  • For display, each entry is shown by its target only: md, mw, rst, tidy, txt, tex. The bare "htm" entry is displayed by first rewriting it to "htm2txt" and then stripping the front -- so it also displays as "txt". The pick list therefore shows txt TWICE (plus htm from the offered keep-original entry).
  • The two txt rows are not the same underneath. One is the real htm2txt converter. The other is the bare "htm" entry, and choosing it leads to a lookup for an Import key named just "htm", which does not exist, so no converter runs, no text is produced, and the command ends with the message "No text!".
  • Verdict: for .htm and .html files, the picker shows a duplicated "txt" entry, and one of the two is a dud. That matches the "duplicate entries" half of your recollection exactly.

Trace three -- the hang risk.

  • The converter is run through runShell with wait turned on, and that wait is WaitForExit with no time limit, on the interface thread. Any converter that blocks -- an Office converter showing a hidden dialog, a tool waiting for input -- freezes all of EdSharp for as long as it blocks. (The Preview Markdown code nearby does this right, waiting at most 15 seconds.) This is the likeliest source of the "or did it hang" half of the memory.

Other defects found

  • Converters whose tools no longer exist. The Import table still defines brf2txt through Convert\NFBTrans, brl2txt through Convert\liblouis, and htm2tidy and html2tidy through Convert\Tidy -- but those folders are gone from Convert (removed in the June pruning). The user guide explicitly documents braille back-translation ("brl:1 brf:1" under ViewLevels), and that documented feature cannot work: the command runs nothing, and the user gets the raw command line in an error box.
  • The Scripts folder is missing from the repository. The installer ships Scripts with a skip-if-absent flag, so a fresh clone builds an installer that silently contains no JAWS scripts, and its JAWS install step then reports FAILED (the script stops when the Scripts folder is absent). Your working folder has the files; the repository does not. Note that tidyRepo will never add them by itself: its rule is that a wildcard in the setup script proves a file is allowed, never that it is wanted, and Scripts is shipped by wildcard.

Documentation defects

  • Two stale commands. Lines 767 and 768 of EdSharp.md document "Insert Script Path, Control+I" and "Insert All Users Path, Control+Shift+I". Those commands no longer exist, and both keys are owned by Next Indent and Prior Indent -- which the same catalog documents correctly a page earlier. The stale pair should be deleted.
  • Ten commands are undocumented. The catalog has no entries for: Preview Markdown (Control+F9), Preview Markdown in Web Browser, Markdown to Plain Text, HTML to Markdown, HTML to Plain Text (the last four are menu-only by design), Hotkey Summary (Alt+Shift+H), Lookup Term (Alt+F7), Translate Language (Alt+Shift+F7), Tutorial (Control+Shift+F1), and Set on Favorite List (Control+L).
  • Three catalog lines are missing the comma between key and description (Delete File, Extra Speech Log, and Rename), which matters to anything that parses the catalog -- including this audit and the Hotkeys file generation.

Checks that came back clean

  • Key names match everywhere once naming style is accounted for: the guide writes human names (Backslash, Equals, 7, RightArrow) where the code uses .NET names (Oem5, Oemplus, D7, Right). All 44 such pairs were checked and each is the same physical key. No genuine key mismatch exists between the catalog and the menus.
  • Every one of the 216 menu items has a click handler, including all nine recently added commands.
  • The evaluator bridge is correct end to end: EdSharp.js declares package EdSharp and class JS with runScript, and the C# loads EdSharp.dll by path and asks for exactly "EdSharp.JS" and "runScript" with matching argument types.
  • The ViewLevels behavior matches its documentation paragraph point by point: explicit entries win, the listed binary formats convert, all text formats open raw, and braille files open raw unless overridden -- though the override then fails for the missing-tool reason above.
  • The commands the guide documents that are not menu items (the Say family under its submenu, and the JAWS-layer keys such as the Grave voice controls and JAWSKey combinations) are correctly outside the menu system rather than missing.

Queued revisions

Code and configuration, in priority order:

  1. EdSharp.ini, Import and Export sections: remove the -S switch from every pandoc line; change markdown_github to gfm; change "-f epub3" to "-f epub" in the epub3 entries. This alone restores Open Other Format for Word, EPUB, HTML, and Markdown sources.
  2. EdSharp.cs, ConvertFile2String: stop offering the dud entry -- when the bare extension entry and a real ext2txt converter would both display as "txt", keep only the real one (or make choosing the bare entry open the file raw, which is what a reasonable person expects "txt" to mean there).
  3. EdSharp.cs, runShell: give the waiting variant a time limit (the 15-second pattern already used for Preview Markdown, or a larger one for big documents), and report a timeout in plain words instead of freezing.
  4. Decide the fate of the toolless converters: either restore NFBTrans, liblouis, and Tidy through FetchConvertTools so the documented braille back-translation works again, or remove those Import entries and the braille back-translation promise from the guide. (Half measures leave the current lie.)
  5. Add the Scripts folder to the repository (a one-time explicit git add; tidyRepo will keep it thereafter), so a fresh clone can build an installer whose JAWS step succeeds.
  6. EdSharp.md: delete the two stale Insert Path lines; add catalog entries for the ten undocumented commands; restore the missing comma on the three malformed lines.

Say the word and any of these arrives as a script in the usual way; the ini and documentation fixes are mechanical, the ConvertFile2String and runShell changes are small and will come with traced test cases.

Summary

The audit cross-checked all 216 documented commands against all 216 menu items and traced the suspect paths by hand. Your recollection about Open Other Format was right twice over: modern pandoc rejects the -S switch that every converter line still carries, so conversions fail with an error box, and the HTML pick list really does show a duplicated "txt" entry whose impostor half produces "No text!". Behind those sit an unlimited converter wait that can freeze the editor, converter entries whose tools were deleted while the guide still promises the feature, and a repository missing the Scripts folder that the installer needs. The documentation needs two stale commands removed, ten new ones added, and three malformed lines repaired. Everything else checked clean, including the evaluator wiring and the ViewLevels behavior. The queued revisions above are ordered so that the first one alone brings back the command you missed most.
